# 封面墙网格布局

封面墙与横滑推荐区共用一套均分度量（契约见 [shell.md](./shell.md) 的「水平分页」）：`--card-w` 是**基准卡宽**，实际渲染宽由容器宽均分得出，左右两侧因此始终贴住视图内边距。

## 规格

```css
.cover-grid {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(min(var(--card-w), 100%), 1fr));
  gap: var(--space-4);
}
```

```js
cols = computeColsFor(el, { gap });   // lib/grid-metrics.js
card = cardWidth(width, cols, gap);   // = (S − gap×(cols−1)) / cols
```

- 基准 `--card-w: 17.3125rem`（277px），gap `--space-4`（16px）；窄档基准 200px，见下节
- 列数 `N = floor((S + gap) / (基准 + gap))`，实际卡宽 `= (S − gap×(N−1)) / N`
- chrome 固定不随视口缩放：侧栏 60px + 视图内边距 32px×2（都是 rem，跟着字号缩放同比例变化），内容区 `S = 窗口宽 − 124`
- 卡片 `aspect-ratio: 3 / 4`，行高 = 卡宽 × 4/3

## 窄档

`lib/narrow.js` 观察 `.shell__main` 的实测宽，低于 1220 时在根元素打 `data-narrow="on"`，`:root[data-narrow]` 里把基准降到 200px。

量主内容区而不是 `window.innerWidth`：侧栏是 rem，字号滑块会改「窗口宽 − 内容宽」这个差值，用视口宽判断会在字号变化后错开 ±30px，而决定列数的始终是内容宽。

阈值取 1220（等价客户区 1280、封面墙 `S = 1156`）的理由是它是宽档**最后一个还能排 4 列**的宽度：再窄 1px，277 只能排 3 列、卡宽涨到 374。窄档只接管这个已经糟掉的区间，不向前侵占宽档的大卡观感。

- **窄档值用 px 不用 rem**：这一档的目的是保密度，rem 会随字号放大把基准推高、反向掉列
- **跨档跳变已知且接受**：客户区 1279 → 1280 时封面墙 5 列 218 → 4 列 277。均分铺设下基准一升列数必减，1280 是唯一能把跳变压到一列的落点

覆盖 `--card-w` 的容器要各自配一条窄档规则，且值不能照抄：

| 容器 | 覆盖位置 | 宽档 | 窄档 |
|---|---|---|---|
| 封面墙 | `tokens.css` | 277 | 200 |
| 详情页角色区 | `views/detail.css` | 220 | 180 |
| 继续游戏 | `views/dashboard.css` | 435 | 360 |

两条约束：

1. **每个覆盖了 `--card-w` 的容器都要自带 `[data-narrow]` 值**。自定义属性在容器上一赋值就切断了继承，`:root[data-narrow]` 改不到它；也不能指望靠导入顺序，`styles.css` 里 `components/hscroll.css` 排在 `views/*.css` 之前，同特异度是后者胜。`[data-narrow] .x`（0,2,0）压得住 `.x`（0,1,0），所以写在容器自己的文件里就行
2. **窄档值按容器自己的可用宽定，不按窗口宽反推**。角色区比封面墙窄 138px（详情页内边距 48×2 + 分区内边距 20×2 + 边框 1×2），同一个 200 拿到角色区只能排 4 列，所以那里取 180。多一列只差 30~40px，凭窗口宽估会算出白改一档的值

## 实测

「窗口」指客户区宽。

| 窗口 | S | 基准 | 列数 | 卡宽 | 行高 |
|---|---|---|---|---|---|
| 1000（最小宽度） | 876 | 200 | 4 | 207.0 | 276.0 |
| 1279（窄档上界） | 1155 | 200 | 5 | 218.2 | 290.9 |
| 1280（宽档起点） | 1156 | 277 | 4 | 277.0 | 369.3 |
| 1440 | 1316 | 277 | 4 | 317.0 | 422.7 |
| 1920 | 1796 | 277 | 6 | 286.0 | 381.3 |
| 2560 | 2436 | 277 | 8 | 290.5 | 387.3 |

窗口最小宽度：`minWidth` 1014，落地客户区 1000（外框与客户区的关系见 [shell.md](./shell.md) 的「窗口尺寸」）。这个宽度落在窄档，4 列需要 `S ≥ 848`，实际 `S = 876`，留 28px 余量。宽档的 3 列门槛（`S ≥ 863`，客户区 ≥ 987）已不是最小宽度的约束点。字号缩放放大时窄档基准不变，列数不会因此掉档。

默认窗口 1920×1114（客户端 1920）落在 1920 那行：左右各 32px，卡宽 286。容器宽 1796 实测：卡宽 286、gap 16、左右余量 0。

## 基准是门槛，不是实际宽度

实际卡宽在基准之上浮动（6 列档 277~326，列数越少浮动越大）。下面三件事依赖卡宽**可预测**而非恒定：

1. **窗口化**（虚拟滚动）—— 行高用实测卡宽算，`row = floor(index / cols)` 用它
2. **详情页 FLIP 转场** —— 起止矩形都从 `getBoundingClientRect()` 实测，不读常量
3. **横滑推荐区与主网格对齐** —— 两侧共用同一套均分式

## 不要加 justify-content: space-between

余量已由轨道吸收。再叠 `space-between` 会让末行不满时卡片被推到左右两端（38 条时最后一行只有 2 张，视觉上断开）。

## 不要用 auto-fit

`auto-fit` 会折叠空轨道：某分区条目少于列数时，剩下的卡片会被撑满整行。`auto-fill` 保留空轨道，卡片保持整列宽。

## 容器宽度由谁决定

`auto-fill` 基于**容器实测宽度**，不是视口。窗口 resize、DPI 缩放都由浏览器和 `ResizeObserver` 处理，不需预测。

列数公式只在 `lib/grid-metrics.js` 一处：CSS 侧靠 `auto-fill` 与 `1fr` 均分，窗口化在 JS 侧用同一函数算出列数与卡宽，再写成显式 `repeat(N, minmax(0, 1fr))`。两侧不同源就会出现「虚拟滚动按 6 列排、实际渲染 7 列」这类错位。

## 窗口化

- 单区达到 60 条启用。
- 行高 = 实测卡宽 × 4/3 + gap，**不取整**：卡宽是分数（1440 下 317），取整会让每行累积误差，几十行后整体错位。
- gap 从 `--space-4` 解析成像素（`pxLength`），不要读 `getComputedStyle` 的 `rowGap`：网格容器 `.virtual-grid` 是 `position: relative` 的普通容器，不是 grid，`rowGap` 恒为 `normal`，`parseFloat` 得 NaN 被兜成 0，行间距整段丢失。
- rem 换算按**根字号**，不按元素自身字号（`pxLength` 取 `documentElement`）。正文是 `1.016rem`（16.256px），拿元素字号换算会把 277 读成 281.4，窗口化按 3 列排而 `auto-fill` 渲染 4 列。
- `data-narrow` 只改 `--card-w`、不改容器宽，`ResizeObserver` 观察不到：网格要监听根元素该属性（`MutationObserver`）强制重算，否则跨阈值那一帧会停在旧基准算出的列数。
- 卡宽或列数变化后必须 `virtualizer.measure()`。`itemSizeCache` 缓存首帧算出的行高，只换 `estimateSize` 不清缓存时，**列数不变而卡片被 `1fr` 拉宽**的区间（放大窗口）仍按旧行高定位，行距逐级压缩直至贴合；缩小时因为列数跨档、虚拟器重建，反而看不出问题。
- 分区不在滚动容器顶部，`scrollMargin` 取网格容器相对滚动视口的偏移；行的 `top` 用 `row.start - scrollMargin`，漏掉会渲染错行。
