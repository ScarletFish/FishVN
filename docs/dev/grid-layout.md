# 封面墙网格布局

封面墙与横滑推荐区共用一套均分度量（契约见 [shell.md](./shell.md) 的「水平分页」）：`--card-w` 是**基准卡宽**，实际渲染宽由容器宽均分得出，左右两侧因此始终贴住视图内边距。

## 规格

```css
.cover-grid {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(min(var(--card-w), 100%), 1fr));
  gap: var(--space-4);
}
```

```js
cols = computeColsFor(el, { gap });   // lib/grid-metrics.js
card = cardWidth(width, cols, gap);   // = (S − gap×(cols−1)) / cols
```

- 基准 `--card-w: 17.3125rem`（277px），gap `--space-4`（16px）
- 列数 `N = floor((S + gap) / (基准 + gap))`，实际卡宽 `= (S − gap×(N−1)) / N`
- chrome 固定不随视口缩放：侧栏 60px + 视图内边距 32px×2（都是 rem，跟着字号缩放同比例变化），内容区 `S = 窗口宽 − 124`
- 卡片 `aspect-ratio: 3 / 4`，行高 = 卡宽 × 4/3

## 实测

| 窗口 | S | 列数 | 卡宽 | 行高 |
|---|---|---|---|---|
| 1000（最小宽度） | 876 | 3 | 281.3 | 375.1 |
| 1280 | 1156 | 4 | 277 | 369.3 |
| 1440 | 1316 | 4 | 317 | 422.7 |
| 1920 | 1796 | 6 | 286 | 381.3 |
| 2560 | 2436 | 8 | 290.5 | 387.3 |

窗口最小宽度：`minWidth` 1014，落地客户区 1000（外框与客户区的关系见 [shell.md](./shell.md) 的「窗口尺寸」）。3 列需要 `S ≥ 863`，即客户区 ≥ 987，1000 留 13px 余量。字号缩放放大时基准跟着变大，这个下限不再保证 3 列。

默认窗口 1920×1114（客户端 1920）落在 1920 那行：左右各 32px，卡宽 286。容器宽 1796 实测：卡宽 286、gap 16、左右余量 0。

## 基准是门槛，不是实际宽度

实际卡宽在基准之上浮动（6 列档 277~326，列数越少浮动越大）。下面三件事依赖卡宽**可预测**而非恒定：

1. **窗口化**（虚拟滚动）—— 行高用实测卡宽算，`row = floor(index / cols)` 用它
2. **详情页 FLIP 转场** —— 起止矩形都从 `getBoundingClientRect()` 实测，不读常量
3. **横滑推荐区与主网格对齐** —— 两侧共用同一套均分式

## 不要加 justify-content: space-between

余量已由轨道吸收。再叠 `space-between` 会让末行不满时卡片被推到左右两端（38 条时最后一行只有 2 张，视觉上断开）。

## 不要用 auto-fit

`auto-fit` 会折叠空轨道：某分区条目少于列数时，剩下的卡片会被撑满整行。`auto-fill` 保留空轨道，卡片保持整列宽。

## 容器宽度由谁决定

`auto-fill` 基于**容器实测宽度**，不是视口。窗口 resize、DPI 缩放都由浏览器和 `ResizeObserver` 处理，不需预测。

列数公式只在 `lib/grid-metrics.js` 一处：CSS 侧靠 `auto-fill` 与 `1fr` 均分，窗口化在 JS 侧用同一函数算出列数与卡宽，再写成显式 `repeat(N, minmax(0, 1fr))`。两侧不同源就会出现「虚拟滚动按 6 列排、实际渲染 7 列」这类错位。

## 窗口化

- 单区达到 60 条启用。
- 行高 = 实测卡宽 × 4/3 + gap，**不取整**：卡宽是分数（1440 下 317），取整会让每行累积误差，几十行后整体错位。
- 分区不在滚动容器顶部，`scrollMargin` 取网格容器相对滚动视口的偏移；行的 `top` 用 `row.start - scrollMargin`，漏掉会渲染错行。
