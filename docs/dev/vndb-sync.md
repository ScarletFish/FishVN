# VNDB 账户同步设计（草案）

> 状态：设计草案，待定稿后并入 `docs/fdd-game-library.md` 的活动集。
> 配套端点细节（`get ulist` / `set ulist`）待补入 `docs/dev/vndb-api.md`。

## 1. 定位与字段集

账户同步把用户在 VNDB 的个人列表搬进本地「用户状态」组，与活动集二的元数据同步走不同通道：元数据同步改写元数据行（含 VNDB 的贝叶斯 `rating`），账户同步改写 `user_game_state` 的 `status` 与 `user_rating`。VNDB 的 `vote`（个人评分）映射到 `user_rating`；VNDB 的 `rating`（元数据）仍不触碰 `user_rating`（与 FDD 活动集二备注一致）。

同步字段首版为两个：`status`、`user_rating`。`notes` 暂不在首版范围，留待后续。身份组、本地安装组、元数据组不在账户同步范围。关联键 `vndb_id` 用于匹配，不参与覆盖语义。

## 2. 三种同步力度

三种力度共享一套三路比对内核，差别只在「采纳 / 保留」动作是否真正写入对方侧。内核依赖一份**基快照**：记录上次成功同步时 VNDB 在那个字段上的值。

对每条记录取三值：基快照 `base`、本地当前 `local`、远程当前 `remote`，逐字段（status 与 user_rating 各自独立）判定：

| base、local、remote 关系 | 判定 | 默认动作 |
|---|---|---|
| 三者相同 | 无变化 | 不动，base 对齐 remote |
| base == local ≠ remote | 仅 VNDB 改了 | 采纳 remote |
| base ≠ local == remote | 仅本地改了 | 保留 local |
| 三者各不相同 | 两边都改了 | 冲突，进面板 |
| base 为空且本地无修改时间 | 本地是初始值 | 采纳 remote |
| base 为空且本地有修改时间 | 无法区分默认值与手设值 | 冲突，进面板 |

基快照的意义：用户上次坚持的本地值，只要与基快照不同，就不会被反复判为冲突；只有用户与 VNDB 都动了同一字段，才上升为冲突。

### 仅下载（首版默认力度）

数据从 VNDB 流向本地，本地从不写回 VNDB。

- VNDB 列表项在本地已存在 → 三路比对，按上表采纳或保留（受导入范围约束，见第 4 节）。
- VNDB 列表项在本地不存在 → 用 `title` 建最小壳：`name` + `vndb_id` + `status`，有 `vote` 时带 `user_rating`（同样受导入范围约束）。这批新 `vndb_id` 归入「刚同步集」，供批量下载资料使用。
- 仅下载只处理 `status` 与 `user_rating`；`notes` 维持本地原值。
- 保留规则的效果：用户本地手改的状态 / 评分，只要不等于基快照，就不会被 VNDB 的旧值覆盖。

### 仅上传

数据从本地流向 VNDB，用 `set ulist` 写出 `status` 与 `vote`（= `user_rating`）。

- 三路比对同上；上传语境下「采纳 remote」读作「仍把本地推上去覆盖远程」。
- 本地有、VNDB 列表没有的条目 → 用 `set ulist` 在 VNDB 新建（带 status 与 vote），会在 vndb.org 真实列表新增条目，首次写入前需用户确认。
- 本地字段只由用户编辑与上传流程产生；VNDB 当前值仅参与基快照比对。

### 双向

两个方向同时生效：下载侧沿用仅下载的保留规则，上传侧沿用仅上传的保留规则。

- 冲突的「保留哪边」默认准则：以 `lastmod` 较新的一侧为准。VNDB 的 `ulist.lastmod` 给出每条修改时间；本地用状态 / 评分的最后修改时间比对，较新一侧的值胜出。
- 时间无法判定时（本地缺修改时间或 VNDB 缺 lastmod）默认保留本地并提示。
- 双向会同时增删两端列表项：本地新条目上传、VNDB 新条目下载建壳。

## 3. 状态与评分映射

### 状态

VNDB 用 labels 表达状态：`playing` / `finished` / `stalled` / `dropped` / `wishlist`（心愿单的显示名在不同资料里也作 `planning`，映射时两种拼写都认），另有 `voted` 标记只投票未设状态。本地 `status` 枚举在现有四个之外增加 `stalled`（搁置），其余与 VNDB 对齐：

| VNDB label | 本地 status |
|---|---|
| playing | 游玩中 |
| finished | 已完成 |
| dropped | 已弃坑 |
| stalled | 搁置（新增） |
| wishlist / planning | 计划中 |

`status` 非空两端一致，无缺省歧义。无法映射的 label 与纯投票条目的处理见「导入范围」。

### 评分

`user_rating` 与 VNDB `vote` 同为 0–100 百分制（`vote` 量程 10–100，对应 1.0–10.0），直接 1:1 写入，不换算。`user_rating = 0`（未评分）对应 VNDB 无 `vote`；VNDB 有 `vote` 而本地为 0 时按「remote 有值」采纳。

## 4. 导入范围（本地优先）

FishVN 是本地库，不是 VNDB 的附属：同步只取对本地有用的数据，导入范围可收窄。

- **心愿单开关**：配置 `vndb_sync_import_wishlist`，默认关闭。关闭时 `wishlist` 条目不建壳、不更新、不进冲突；开启后按「计划中」正常参与同步。
- **纯投票条目恒跳过**：没有任何状态 label 的条目（如仅 `voted`）不导入、不更新、不参与比对，与开关状态无关。
- **未知 label 跳过并警告**：既非五个状态 label 也非 `voted` 的条目跳过，并在同步结果中提示。
- 跳过计数进入同步计划的 `skipped`，只在弹窗汇总行占一格；导入范围本身在设置页调整，结果弹窗不重复解释规则。

跳过的安全性由三路比对保证：跳过期间不写本地、不写基快照。之后开启开关时，本地未再动过的条目按「仅 VNDB 改了」正确采纳；本地动过且 VNDB 也改了的条目判冲突——过期基快照不会把错误的值静默写入。

## 5. 数据模型

- 用户状态表增加两个可空列，记录基快照：`synced_status`、`synced_rating`。
- 用户状态表增加一个修改时间列，记录 status 与 user_rating 的最后本地修改，供双向 `lastmod` 比对。
- `Status` 枚举增加 `stalled` 变体；字符串映射同步更新，`status` 列为 TEXT，旧数据不受影响，不写旧库迁移。
- 开发期直接改建表语句（项目约定）。

## 6. 端点、鉴权与限流

- 读取用 `get ulist`（Kana v2 已合并 vnlist / votelist / wishlist），条目顶层 `id` 即 vn id，标题随 `vn.title` 内联返回（响应形状详见 `vndb-api.md`）。首版只取 `id, vn.title, labels, vote, lastmod`。
- 写入用 `set ulist { status→labels, vote }`；无对应条目时即新建。
- 翻页用 `results`（上限 100）+ `page`，以响应 `more` 决定是否续页。限流按 `vndb-api.md` 保守口径（100 请求 / 5 分钟客户端节流）执行，500 部约 5 页，余量充足；429 按退避重排。
- 计划短缓存：拉取生成的计划在内存中缓存 60 秒，期间重复触发同步直接复用，不打 VNDB。**应用落库、切换同步力度、切换「导入计划中的游戏」、保存或清除 token 都会立即使缓存失效**——缓存只防连点与重复拉取，不改变「计划不落库、可反复重新生成」的语义。
- 鉴权：请求头 `Authorization: token <token>`。
- token 存储：存本地 `config.json`，但以「固定掩码 XOR + hex」混淆落盘、**不存明文**。本地单机 + 只读凭证场景下，混淆只防配置文件被误提交进 git、被 dotfiles / 云盘同步、被截图或随手打开；防不住本机内存抓取型恶意软件。因此不引入加密依赖，零新增 crate。
- UI 入口在设置页：粘贴 token 后点「保存」（回车等效）落盘，随即自动发一次 `get ulist results=1` 验证（401 即无效），输入框清空、结果交给状态行；输入框为空时按钮转为「验证」，测的是已存的那份，不必重新粘贴。「清除 Token」是状态行末尾的文字动作。前端只持有本次会话用户输入的原始 token，不碰落盘密文；打开设置时后端只回 `has_token` 布尔。UI 标注 token 等同只读凭证、只发往 `api.vndb.org`。

## 7. UI 落点

同步分两段：**拉取计划**与**确认应用**。点「立即同步」只拉取 VNDB 列表并与本地三路比对，生成一份不落库的计划；用户在弹窗里确认（勾选导入、裁决冲突）后，应用动作在一个数据库事务里一次性写入。取消即零副作用——这是 git「fetch → review diff → apply」的同款颗粒度，与冲突面板「先看后选再应用」是同一个交互模型。

- 设置页「VNDB 同步」tab：粘贴 token → 保存并自动验证（已存时按钮转为「验证」）、清除、选择同步力度（默认仅下载）、「导入计划中的游戏」开关（默认关）、「立即同步」按钮（未保存 token 时不可点）。
- 同步计划弹窗：点「立即同步」即弹出，先进入加载态，计划生成后切换到结果内容。全部条目与本地一致时展示「已经是最新状态」空态而非轻提示——弹窗本身就是回执。全量跳过必须展示——空态会掩盖整表被跳过的事实。
  - 加载态：转环 + 阶段文案（拉取账户列表 / 比对本地库）+ 进度条（拉取阶段有总数时 determinate，比对阶段 indeterminate）+ 已拉取条数与已用秒数 + 「取消」。取消关闭弹窗并丢弃结果，不写入任何更改；后台拉取会跑完，计划缓存随之刷新，下次同步直接复用。
  - 阶段进度经 `vndb-sync-progress` 事件通道播报（TaskEvent：`phase` 为 `fetch` 时 `done`/`total` 是已拉取条数与列表总数，`plan` 表示进入本地比对阶段）；开发模式下同一事件经 EventLog 走 SSE。加载态的阶段文案只消费事件，不虚构阶段。
  - 失败态：错误信息 + 「重试 / 关闭」，重试重走完整拉取。
  - 汇总行：共 N 部打头，后接待确认冲突 / 新增导入 picked/total / 更新 / 跳过，只列非零项；导入计数随勾选联动。
  - 计划说明一行：改动在确认后才写入游戏库。取消的后果不再单独成段——「确认后才写入」已含此意，重复一遍只增加阅读量。
  - 冲突区：每部作品一行，status 与 user_rating 各自并排显示本地与 VNDB 的值，点选一侧即选中；默认全选本地；提供「全部保留本地 / 全部采纳 VNDB」批量操作。
  - 新增导入名单：按状态分组（组头 = 组级全选 + 状态名 + 计数），组内每部作品一个双选 chip——**实心 = 在表单里（要导入，默认全选），幽灵 = 不选**，点一下即两态切换；chip 内只放作品名，所属状态由分组自明。导入是库内容的变化，必须对用户可见且可控。
  - 更新不列名单（首次同步可能上百条），只占汇总行一格；跳过同样只占汇总行一格（计划中与仅投票的作品不参与，导入范围在设置页调整）——规则不随结果重复解释。无法映射的 label 在此以用户视角的警告呈现。
  - 底部动作：有可应用内容时为「取消 / 应用更改」；纯跳过无警告时单个「完成」。
- 应用为单命令提交：勾选的建壳、采纳的更新、基快照刷新、冲突裁决在一个事务里落库；写入后关闭弹窗，通过配置变更事件通知各视图刷新。本次有新建条目时随后弹一次「下载资料」确认（开始下载 / 稍后），确认后按 `created_ids` 启动批量补全——下载是独立于落库的第二步联网动作，放在条数已知之后再问。
- 计划不落库：内存短缓存 60 秒（见第 6 节），过期或失效后下次同步重新生成。VNDB 上有的条目不隐藏——这次没导入的，下次同步仍在名单里，可再勾掉。

## 8. 实现边界与风险

- 首版只实现仅下载：拉取 ulist、三路比对、生成计划、计划确认弹窗与应用。同步力度选仅上传 / 双向时，同步命令明确报错尚未做好，不在前端隐藏入口。
- 仅上传与双向会向 vndb.org 真实列表写入 status 与 vote；力度切换与首次写入前需用户确认。
- 鉴权失败（401）不抹本地数据，明确报错。拉取过程中网络中断时本次同步整体失败、可重试；计划阶段不写库，应用阶段为单事务，均无部分写入。
- 新作品建壳的名称来自 ulist 内联的 `vn.title`（一次翻页请求带回，不按 id 二次查询）；VNDB 查不到标题时以 vndb_id 作名称占位。元数据（封面、标签、角色）不随同步拉取，由用户按需触发元数据同步或批量下载。
- 图片不属 ODbL，缓存随应用数据走，清应用数据即删（见 `vndb-api.md` 使用条款）。

## 附：批量下载 VNDB 数据（资料补全，与账户同步解耦）

- 触发入口两处，作用域二选一：列表工具条按钮扫全库资料不全的游戏；同步计划应用成功后在确认弹窗里选「开始下载」，只对本次新建的条目补全（传 `created_ids`）。两处触发都即时显示忙态与常驻状态栏，不等首个进度事件。
- 已绑定的按 `vndb_id` 直拉；未绑定的按作品名搜索 VNDB，取第一条自动绑定后拉取，搜索无结果跳过并计数。
- 补丁只填空白列，已有内容不动；角色集为空的整包写入。
- 拉取走限流器，触发 429 冻结约 5 分钟等待恢复；进度、未匹配与失败计数、完结汇总走任务事件通道，由底部居中的浮动状态面板展示（非详情页，可手动收起，完结数秒后自动隐藏），支持取消与暂停。
- 面板错误列表不按事件逐条堆：文案相同者合并成一条并记次数，列表封顶 20 条（超出记数），限流提示只走徽标不进列表——限流期间每个条目都会报同一句，逐条入列会刷满并触发重复 key。
- 每完成一部即时广播一次库变更（item 级，载荷带 `game_id`），跑完再广播整体变更与标签变更：详情页与角色区按 id 认领自己那部，一部只刷一次、不为别人的进度空转；列表与首页是重查询，把连续多部合并成 5 秒一批。视图不必等整个任务结束才看到新封面。
- 查询任务状态失败时不清面板：一次查询失败就让面板消失会连暂停与取消入口一起丢掉，而后端任务仍在跑。
- 暂停是"顺延"而非丢改动：标志只在条目边界生效，当前这一部会跑完并整部落库，恢复后从下一部继续；取消则打断飞行中的请求，当前这一部不写入（写入是整部一次提交，库里不留半残条目），已完成的全部保留。因此暂停后到真正停下之间有一段"收尾"时间，面板此时显示「正在暂停…」而不是「已暂停」——后端在 `wait_resume` 真正阻塞时置 `paused_idle` 并补发 `paused` 事件，前端据此切换；刷新后靠状态的 `paused_idle` 字段还原，不猜时间。
