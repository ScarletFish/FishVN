# 补全提速：批量取数与两阶段图片池（执行台账）

> 本文件是执行台账，不是产品规格。记录实测依据、语义约定、分步做法与进度，供接手或上下文丢失时对照。

## 一、实测依据

130 部、缩略图模式下的时间构成（取自 `单部耗时` / `请求分解` 两条 debug 日志）：

| 环节 | 单部 | 130 部 | 占比 |
|---|---|---|---|
| 元数据（含角色行） | 3.7 s | 480 s | 40% |
| 角色立绘（部内 8 并发） | 3.5 s | 455 s | 38% |
| 封面（缩略图） | 1.5 s | 195 s | 16% |
| 落库 | 0.1 s | 13 s | 1% |
| 合计 | 8.8 s | ~1140 s（19 分钟） | — |

四条判定：

1. **限速不是瓶颈**：每部只有 2 次 `acquire`，全程 `限速 0ms`，桶的 100 请求 / 5 分钟从未排上队。
2. **耗时归到同一件事**：这条跨境线路的带宽，加上每次请求的固定开销。单部全字段请求 3~5 秒，其中传输只有 0.8 秒。
3. **批量是线性于体积，不是线性于条数**：

   | 批量 | 响应体 | 耗时 | 折合每部 |
   |---|---|---|---|
   | 5 部 | 80 KB | 2.8 s | 0.57 s |
   | 10 部 | 171 KB | 6.8 s | 0.68 s |
   | 20 部 | 359 KB | 13.7 s | 0.69 s |
   | 50 部 | 819 KB | 34.6 s | 0.69 s |

   收益来自省掉每次请求 2~4 秒的固定开销。
4. **图片并发确实提吞吐**：8 张缩略图（约 380 KB）串行 16.8 s / 22.6 KB/s，8 并发 9.2 s / 41 KB/s，16 并发 11.6 s / 65 KB/s。

体积基线（开发库实测）：

| 类型 | 张数 | 合计 | 平均 | 中位 | 最大 |
|---|---|---|---|---|---|
| 立绘 `ch` | 429 | 9.94 MB | 23.7 KB | 22.8 KB | 52 KB |
| 封面 `cv`（原图） | 66 | 11.11 MB | 172 KB | 123 KB | 4.06 MB |

## 二、脚本与接口事实

- VNDB 的 `id` filter **不接受数组**：`["id","=",["v17","v11"]]` 返回 400 `Invalid 'id' filter: Invalid value.`，`in` 算子也不存在。
- 批量必须写 `["or", ["id","=","v17"], ["id","=","v11"], …]`，50 个条件实测正常。
- 批量请求对**不存在的 id 静默省略**，不报错。只能靠「请求 N 个、返回 M 个」比对出缺失。
- `/character` 可按 `vns` 批量过滤，字段集沿用 `CHAR_FIELDS`。
- 官方硬约束：200 请求 / 5 分钟、每分钟 1 秒执行时间、单请求执行超 3 秒 abort。实测 20 部全字段 13.7 秒未被 abort，说明这 13.7 秒里绝大部分是传输而非执行。

## 三、目标结构

**阶段 1 · 资料**

- 每批 20 部：1 次 `/vn`（`or` 组合）+ 1 次 `/character`（`vns` 过滤）
- 逐部落库，只写资料字段，图片列留空
- 批内不响应取消

**阶段 2 · 图片**

- 全局任务池，16 并发
- 封面任务带 `(game_id, image_id, url, thumbnail)`，回填 `game_metadata.image_path`
- 立绘任务带 `(game_id, character_id, url)`，回填 `characters.image_path`（主键即 `(game_id, id)`，可精确定位）
- 完成一个回填一列并推送该条，不重写整行

## 四、语义约定

| 项 | 约定 |
|---|---|
| 条目状态 | 一批 20 条同时进 `active`，回填后整批 `ok` |
| `ok` 的含义 | **资料完成**；图片可能仍在下载。封面/立绘缺失只记 warn，不翻状态 |
| 进度 | 资料阶段按部计数、步长为批大小；图片阶段复用 `images` 阶段名，按张计数 |
| 库变更推送 | 仍逐部推 item 事件（载荷不变），前端 5 秒节流会合并 |
| 单条失败 | 按 id 比对，缺失的标 `failed`，原因「VNDB 未返回」 |
| 整批失败 | 重试 2 次，仍失败则全批 `failed` |
| 取消 | 资料阶段**批边界**生效，当前批跑完并落库后不再开新批；图片阶段**立即中断**（幂等，半截不写盘） |
| 暂停 | 与取消同构：资料批边界、图片立即中断 |
| 图片失败 | 3 次重试与退避不变，最终失败只记 warn |
| 落库粒度 | 逐部事务，不合并成批事务 |
| 未绑定条目 | 绑定阶段保持逐部搜索，绑定完再进批量 |
| 限速 | 按请求数计数：一批 2 次 `acquire`，移到批发起前 |
| 批大小 | 20（常量；50 部一次 819 KB / 35 秒，一次失败太重） |
| 图片并发 | 16（常量，不进设置） |
| 单条重试 | `backfill_single` 走原单部路径，语义不变 |

## 五、分步做法

1. **骨架**：`run` 改为「资料批循环 → 图片池 → 收尾」，先把单部包成一批（批量 = 1），确保状态、推送、进度与现状等价
2. **批量取数**：`fetch_batch` 用 `or` 组合取 `/vn` 与 `/character`，按 id 比对缺失，拆出逐部落库
3. **图片池**：`image_jobs` 收集器 + `JoinSet` 16 并发 + 逐张回填与推送
4. **取消/暂停**：资料阶段去掉 `select` 监听，图片池保留；批前检查标志
5. **UI**：补全页与任务坞补「正在停止…」态；资料/图片两段进度
6. **测试**：axum 本地 mock（固定字节 + 可控延迟），测并发结构、404 回退、失败重试、取消边界
7. **文档**：`vndb-api.md` 补批量过滤写法与缺失语义；FDD 活动集二补 `ok` 的新含义

### 步骤 2~7 落地记录

`run` 现在是三段：

```
绑定（逐部，仅无 vndb_id 的条目搜索）
  → 资料（20 部一批：/vn 一次 + /character 分页，逐部落库，批末推进度与推送）
  → 图片（16 并发池，逐张回填 image_path，按 game_id 去重推送）
```

- 批内不响应取消；`fetch_chunk` 只在限流（429，冻结 5 分钟）与整批失败时重试，整批最多再试 2 次
- 缺失 id 由 `assemble` 求差得出，逐条标 `failed`，原因「VNDB 未返回」
- 图片池的完成数经 `StatusMirror` 同时写进 `BackfillStatus`（`stage` / `images_done` / `images_total`），
  前端据此切第二段进度；事件面不变，仍是 `images` 阶段 + 全局 done/total
- `download_images` 改为接收 client（原为内部取全局客户端），并发结构与失败路径因此可测；
  5xx 纳入重试（原先只有网络错误重试，5xx 直接失败）
- 取消生效于批边界后，收尾把仍是 `active` 的条目退回 `pending`，列表不留悬挂态

单条路径（`backfill_single`、`fetch_vn_metadata`、devhttp）不变。

### 实测（2026-11-08，开发库 129 部）

| 轮次 | 范围 | 耗时 | 结果 |
|---|---|---|---|
| 首次全量 | 64 部待补 | **73 秒**（资料 37 秒 + 图片 36 秒） | 61 成功、3 失败 |
| 修复后复跑 | 3 部 | 4.5 秒 | 全部成功 |
| 线路慢时段 | 30 部 | 78 秒 | 全部成功 |

首次全量那 3 部失败的原因是「同一个游戏里出现重复的角色 id」：同一角色在同一作品有多条
`vns` 记录（不同 release），按 `vns[].id` 分组时同一行被收进同一个桶两次，产出了重复角色。
分组后加 `sort + dedup` 修掉。

第二轮又撞到两件事，都已修：

- **20 部一批的角色请求会超时**：这批 20 部的 `/character` 全字段超过 150 KB，在慢时段
  （同一条线路凌晨 10 秒、下午 60 秒）直接撞上客户端 20 秒总超时，整批 20 部被判失败。批量
  请求改用 45 秒超时，并把角色按 10 部一组拆开并发——同一批从 61~87 秒降到 32 秒
- **`/vn` 批量同样要宽超时**：全字段 20 部也有 300 KB 以上

修完复跑 30 部：20 部批 31.8 秒、10 部批 40.5 秒，全部成功，图片 212 张全部落盘。
全库现状：129 部资料齐、871 位角色、13 位无立绘（VNDB 本身没有）。

### 步骤 1 落地记录

当前是中间态：**资料仍逐部串行，图片已统一进池**。

- `fetch_sync` 不再下载图片，返回 `(VnSync, Vec<ImageJob>)`；`map_characters` 同步改为返回角色图任务
- `ImageJob { game_id, kind: Cover | Character { character_id }, image_id, url, thumb }`
- `run` 在资料循环结束后调 `apply_images`：`download_images` 16 并发 → 逐条 UPDATE 回填 → 按 `game_id` 去重推送
- 回填条件都带空值判断（`COALESCE(image_path,'') = ''`），不覆盖用户已设的封面与立绘
- 图片阶段取消立即中断（`abort_all`），已下载的照常回填
- 单条路径（`backfill_single`、`fetch_vn_metadata`、devhttp）仍走「下载后填回 `VnSync`」的原语义，用 `vndb::fill_image_paths`

预期效果：130 部从 19 分钟降到约 12 分钟（资料仍占 480 s，图片从 650 s 压到约 230 s）。
